## How a rejection gets recorded

When an order line can't be filled as requested, it's flagged with a rejection reason rather than silently reduced. Open orders (the `shipments` table) carry a single `Rj`/`Rejection_Description` pair. Historical orders (the `historical` table) carry both a primary and an optional secondary rejection reason (`RJCTN_RSN_PRIM_CD`/`_DESC`, `RJCTN_RSN_SECO_CD`/`_DESC`) — see `docs/reference_codes.md` for the full code list.

## How a cut gets recorded

A cut is the gap between what was ordered and what was actually delivered on a historical order line (`historical.CUT_QTY == historical.ORDR_QTY - historical.DELV_QTY`). Every cut line carries a primary cut reason (`CUT_RSN_PRIM_CD`/`_DESC`); a portion also carry a secondary one. `"Allocation"` is one such reason, used when the material's parent product was flagged on-allocation (`allocation.ALLOC_STATUS == 'On Allocation'`) during the order's planned goods-issue week — that's what makes a cut traceable back to a real allocation constraint rather than an unexplained shortfall.

## How a block gets recorded

Open-order lines (`shipments`) and historical delivery headers (`historical.DELV_HDR_BLK_CD`) can each carry a delivery block. `shipments` additionally distinguishes delivery, billing, and credit blocks as three separate fields, since each stops the order for a different reason (fulfillment hold, invoicing hold, and payment-risk hold respectively).

## Order types excluded from fill-rate and on-time metrics

`historical.ORDR_TYPE_CD`/`_DESC` marks each line as Standard, Return, Free Goods, Sample, or Intercompany. Fill-rate, cut, rejection, and on-time metrics are meant to be computed over Standard order lines only — returns, free goods, samples, and intercompany transfers aren't customer-facing sales and would distort those rates if included. `historical.CANCELLED_FL == 'YES'` lines should also be excluded from fill-rate math (a cancellation isn't a shortfall the supply chain caused), though the raw `CUT_QTY` field is still populated for them (see `docs/data_dictionary.md`).

## Fill rate — which one?

This dataset supports three distinct fill-rate definitions, and they should not be mixed:

- **Historical (unit) fill rate**: `SUM(historical.DELV_QTY) / SUM(historical.ORDR_QTY)`, over Standard, non-cancelled lines. A backward-looking, realized rate.
- **Forward (open-order) fill rate**: `SUM(shipments.Confirmed_Qty) / SUM(shipments.Order_Quantity)`. What SAP currently expects to ship against the open book — not yet realized.
- **Dollar fill rate**: either of the above computed on `*_VAL`/`GTS_*` value columns instead of quantity columns.

See `docs/data_dictionary.md` for exact column definitions.
